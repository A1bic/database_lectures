
Откуда появилась идея абстрагирования данных? Сначала всё началось с архитектуры фон Неймана, где появилась однородность памяти - концепция хранения данных и инструкций в одном месте. 
Потом появилась первая абстракция данных - **хранение в файле**. 
Хоть в *ОЗУ* читаемость не нужна, однако в постоянной памяти она необходима для упрощенной работы (имя файла, имя каталога) -> -> ->

> Появляется первая **файло-серверная архитектура**.

В данной архитектуре всё хорошо до момента, когда приложение становится не одно, а `n` штук -> Каждое приложение будет блокировать этот файл, конечно мы таким образом можем соблюдать целостность данных, но файл в один момент может стать очень большим + нельзя поддерживать параллельный доступ -> **Сильное** падение *производительности*.

Конечно можно попытаться хранить несколько файлов с разделением данных на какие-то группы, но все равно так или иначе запросы будут запрашивать те комбинации файлов, которые всё равно будут пересекаться.

Всё остальные попытки оптимизировать данную систему не приведут ни к чему хорошему -> постоянное переписывание кода из роста и частого изменения данных и так далее.

В итоге появляется клиент-серверная архитектура - СУБД (Система Управления Базами Данных) -> Моделирование данных, из-за чего мы избавляемся от привязанности к определенному формату файла.

Таким образом мы получаем целостность данных, которая контролируется СУБД и повышается производительность в следствие группировки запросов по времени и другим параметрам. Однако появляются правила моделирования бизнес-сущностей.

### Виды СУБД
#### Реляционная:

Особенности:
- [ACID](^#asid) свойства 
- SQL запросы
- Организует данные в виде двумерных таблиц 

Преимущества:
- Благодаря механизму ключей, ограничений и транзакций обеспечивается целостность данных и непротиворечивость данных.
- Использование SQL, как стандарта, облегчает разработку и поддержку приложений, а так же миграцию данных между системами.
- Процесс нормализации позволяет устранить избыточность данных и аномалии.

Недостатки:
- Изменение структуры таблиц на работающей системе может быть сложной и дорогой операцией.
- [_Горизонтальное масштабирование_](#^horisontal-scaling) реляционных БД сложнее реализовывать по сравнению с некоторыми NoSQL решениями.
- Сложные JOIN-запросы могут выполняться очень медленно.
- Не имеет хорошую эффективность при хранении данных имеющих древовидную (иерархических) или графовых данных.

#### Документоориентированная:

Преимущества:
- Возможность _изменения_ структуры документов **без** _необходимости модифицировать общую_ схему БД

- Документы в формате JSON или BSON естественным образом отображаются на объекты в языках программирования.

- Простота [горизонтальной масштабируемости](#^horisontal-scaling)


Недостатки:
- Ограничения целостности данных. (Труднее гарантировать, что данные между разными документами согласованны)

- Сложность запросов (Из за структуры документов, менее читаемый синтаксис)

- Потенциальная избыточность (повторение одинаковых данных в нескольких местах. Например, если есть таблица `Заказы` и в каждой строке хранится полный адрес клиента, то этот адрес повторяется для всех заказов одного клиента.) 

Применение:
- Хранение логов
- Разработка MVP
- Данные неструктурированы 
- Обработка больших объемов данных

#### Графовая:

Преимущества:
- Запросы, направленные на поиск путей, обход графов или анализ связей, работает очень быстро
- Нет жестко фиксированной схемы
- Легко добавлять новые типы связей и узлов без необходимости пересмотра всей структуры данных.

Недостатки: 
 - Сложность [горизонтальной масштабируемости](#^horisontal-scaling)
 - Сложность запросов.
 - Ограничение транзакций при больших нагрузках.

#### Ключ-значение (KV - Key Value)

Особенности:
- Данные организованны в виде пар ключ-значение
- Значения могут быть произвольного типа

Преимущества:
- Высокая скорость чтения и записи.
- Простота и легкость масштабирования
- Надёжность, устойчивость к нагрузкам

Недостатки:
- Не подходит для сложных запросов (выборки данных, агрегации и тд)
- Не поддерживает сложное моделирование связей между данными

Применения:
- Кеширование 
- Хранение сессионных данных 
- Реализация очередей
- Хранение конфигов


#### Временные ряды

Преимущества:
- Оптимизация на высокую скорость записи
- Позволяет легко делать агрегации и интерполяции
- Хранение больших объемов данных
- Быстрый доступ к данным

Недостатки:
- Высокая нагрузка на хранение и индексацию
- Сложность выполнения сложных аналитических запросов
- Ограниченный функционал (Некоторые TSDB не поддерживают транзакции, ограничения целостности или полноценные [ACID-свойства](#^asid))

Применения:
- Логирование
- Мониторинг
- Финансовые рынки

#### Векторная:

Преимущества:
- Позволяет быстро выполнять запросы поиска похожих векторов благодаря специальным индексам и алгоритмам.

#### Хранилище данных:

Особенности:
- Используется для хранения документов, изображений, видео, аудиофалов
- Располагаются в каталог и подкаталогах
- Хранит помимо файлов метаданные
- Доступ к файлом осуществляется по их именам и путям в файловой системе

Преимущества:
- Интеграция с операционными системами и стандартными программами для работы с файлами.
- Позволяет выстраивать сложные модели доступа
- Позволяет разворачивать CDN (Content Delivery Network)

Недостатки:
- Поиск осуществляется только по метаданным и именам файлов, а не по их содержимому

#### Колоночная

Особенности:
- Вместо того, чтобы хранить каждую запись целиком, данные организуются по столбцам
- Относятся к семейству NoSQL

Преимущества:
- Высокая производительность аналитических запросов
- Эффективное сжатие данных 
- Улучшенная производительность ввода - вывода
- При [горизонтальном масштабировании](#^horisontal-scaling) почти линейное увеличение производительности


Недостатки: 
- Плохо работает с [OLTP](#^oltp)
- Проблемы синхронизации

Применение:
- BIG DATA
- OLAP - системы

#### Определения

> [!info] _Горизонтальное масштабирование_^horisontal-scaling
> Подход к увеличению производительности и емкости системы путем **добавления новых серверов (узлов) в кластер**, а не усиления одного сервера. Проще говоря, вместо того чтобы купить один суперкомпьютер (вертикальное масштабирование), вы используете несколько обычных машин и распределяете нагрузку между ними. 


> [!important] AСID в контексте баз данных ^asid
>### **A — Atomicity (Атомарность)**
>
Транзакция выполняется целиком или не выполняется вообще. Если одна операция внутри транзакции не удалась, откатываются все изменения.
>
>### **C — Consistency (Согласованность)**
>
>После завершения транзакции база данных должна оставаться в согласованном состоянии — данные соответствуют правилам, ограничениям и логике системы.
>
>### **I — Isolation (Изолированность)**
>
Параллельные транзакции не должны мешать друг другу. Выполнение транзакции выглядит так, будто она работает в одиночку.
>
>### **D — Durability (Надёжность/Долговечность)**
>
>После фиксации транзакции (commit) изменения сохраняются окончательно и не пропадут даже в случае сбоя системы.


> [!example] OLTP ^oltp
>  Это Online Transaction Processing, конкретно класс систем предназначенных для обработки операционных, часто повторяющихся транзакций в реальном времени.
>  
>  Быстрые, короткие транзакции, такие как: покупка в интернет магазине, перевод денег, бронирование билета.
>  
>  Большое количество одновременных пользователей 
>  
>  Строгая консистентность данных - выполнение ACID


> [!example] OLAP
>  Системы позволяют пользователям **анализировать данные**, выполнять сложные запросы и получать агрегированную информацию для принятия решений.

### Моделирование бизнес моделей сущностей

Экземпляр (Instance) - это конкретный, реальный представитель этого типа, "Заполненный шаблон"

Сущность - это тип, описание, "шаблон", "концепция" объекта.


В чем состоит идея моделирования, выделения значимых аспектов сущностей и разных целей формирование различного моделирования

Выделяют 2 основания классификаций:

1. Трехуровневая архитектура (ANSI / SPARC)
	- Внешний
	- Концептуальный
	- Внутренний (физический, исходный)

*Внешний уровень* определяет базу данных с точки зрения конечного пользователя, например: для студофиса важно знать возраст определенного студента, но хранить возраст не удобно 

*Концептуальный уровень* - на этом уровне накладываются ограничения на данные, определяются сущности и атрибуты, семантика данных.
Например: 
На рейтинг компании может быть Exelent, good... на внешнем уровне, однако на концептуальном он может быть как 5, 4... Это надо для удобной группировки данных и так далее

*Внутренний уровень* - на этом уровне все то, что организует производительность, безопасность, структуру файлов, шифрование и разграничение доступа к файлам/данным

2. Уровни моделей данных
	- Сущность-связь
	- Логический уровень
	- Физический уровень

*Сущность-связь (ER - Entity Relation)* - формирование абстракций объектов, появление связей.

*Логический уровень* - то, как мы пытаемся описать объекты выделяя какие-то формальные множества.

*Физический уровень* - выбор СУБД на основе *логического уровня*, то какие типы данных использовать для хранения определенных данных, какие оптимизации применить для получения производительности и так далее.

Сущность - множество экземпляров, реальных или абстрактных однотипных объектов предметной области 

Также выделяют 2 типа сущности: 
- Сильная
- Слабая

Студент - это сильная сущность потому что может существовать сама по себе.

Группа - это слабая сущность, потому что группа не может существовать без студентов

Также сущности могут иметь атрибуты
- Составные (ФИО)
- Простые (фамилия, имя. отчество по отдельности)

Сущности также могут быть: 
- Однозначными - хранят одно значение(например номер)
- Многозначными - хранят не меньше 1 значения, например контак хранящий JSON с множеством телефонов.

Из этого всего появляются 3 вида связи: 

One-To-One, например 1 студент может иметь только 1 паспорт - 1 студент сопоставляются с 1 паспортом.

One-To-Many, 1 группу сопоставляется множество студентов.

Many-To-Many множество групп сопоставляется с множеством студентов.
