Выделяют 5 информационных процессов: 
 - Сбор информации
 - Обработка информации
 - Хранение
 - Передача
 - Представление
 И эти процессы хотелось бы автоматизировать.

До появления CS как науки все эти процессы существовали в пределах небольших библиотек, в которых книги искались линейным или бинарным поиском. Однако библиотеки увеличивались, появлялись картотеки и каталоги.

Тем не менее определение информации так и не сформировалось до конца по многим философским вопросам: Что такое информация? Может ли она существовать без человека? 
Поэтому информацию стоит воспринимать как триединство: **сигнала**, **данных** и **знаний**.

Позже на основе трудов Гёделя и Джона фон Неймана была сформулирована некое определение данных. 

>*Данные - это информация, которая закодирована заранее обговоренным способом

>*Данные* - поддающиеся многократной интерпретации представление информации в формализованном виде, пригодном для **передачи**, **интерпретации** и **обработки**.

Из этого появляется моделировать данные. Но у моделей появляются свои ограничения.

**Например**:

| Студент | Группа | Дисциплина | Преподаватель | Аудитория | Время |
| ------- | ------ | ---------- | ------------- | --------- | ----- |
| ...     | ...    | ...        | ...           | ...       | ...   |

- **Что это:** Все данные в одной большой таблице.
    
- **Плюсы:** Легко найти информацию о конкретном студенте или дисциплине.
    
- **Минусы:**
    
    - Если у студента несколько дисциплин, нужно либо дублировать строки для каждого предмета, либо пытаться хранить несколько дисциплин в одной ячейке (что неудобно для поиска и анализа).
        
    - Трудно составить расписание для преподавателя: чтобы узнать, где и когда он ведет занятия, нужно перебирать много повторяющихся данных.

Поиск конкретного студента реализовать легко, но вот что делать если нам нужно 
найти несколько дисциплин для одного студента? Тогда приходит другая реализация

| Студент | Группа | Дисциплина 1 | Дисциплина 2 | Дисциплина 3 |
| ------- | ------ | ------------ | ------------ | ------------ |
| ...     | ...    | ...          | ...          | ...          |
- **Что это:** Попытка хранить все дисциплины студента в одной строке.
    
- **Плюсы:** Легче видеть сразу все дисциплины студента.
    
- **Минусы:**
    
    - Сложно добавлять новые дисциплины (нужно добавлять новые колонки).
        
    - Если нужно найти все занятия конкретного преподавателя — неудобно.
        
    - Невозможно гибко работать с данными, когда количество дисциплин разное у разных студентов.

Но в ней мы не сможем запросто составить расписание для какого то преподавателя. Тогда приходит идея разделить на несколько табличек студентов:

| Номер студента | ФИО студента |
| -------------- | ------------ |
| ...            | ...          |

Для групп:

| Номер группы | Факультет группы |
| ------------ | ---------------- |
| ...          | ...              |

Для предметов: 

| Номер дисциплины | Название дисциплины | Преподаватель |
| ---------------- | ------------------- | ------------- |
| ...              | ...                 | ...           |

- **Что это даёт:**
    
    - **Целостность данных:** информация не дублируется, легко обновлять (например, если преподаватель меняется — меняем только в одной таблице).
        
    - **Гибкость:** можно создавать связи «студент → группа», «группа → дисциплина», «дисциплина → преподаватель».
        
- **Минусы:**
    
    - Чтобы получить полную информацию (например, все дисциплины студента с именами преподавателей и аудиториями), нужно объединять несколько таблиц через **JOIN** в базе данных.
        
    - Это делает запросы чуть медленнее по сравнению с одной «плоской» таблицей.

В этом случаи повышается целостность данных, но уменьшается производительность системы, и в итоге мы не сможем найти идеального решения
